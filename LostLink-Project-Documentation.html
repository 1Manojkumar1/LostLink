LostLink

Smart Campus Lost & Found Platform

A full-stack MERN application that helps students report, search, match, verify, and recover lost belongings on campus using weighted similarity matching and secure ownership verification.

Technology: React • Node.js • Express • MongoDB

1. Problem Statement

On most campuses, lost-and-found relies on scattered channels:

  • WhatsApp groups where messages get buried
  • Physical notice boards that nobody checks
  • Social media posts with no structure
  • Word-of-mouth that reaches very few people

Result: Students who lose items have no centralized place to report them. Students who find items have no way to reach the owner. There is no structured matching, no verification before handoff, and items go unreturned.

2. Solution

LostLink introduces a structured, campus-wide lost-and-found workflow that centralizes the entire process into one platform:

  1. Report — Students report lost or found items with detailed information
  2. Search & Filter — Other students search and filter reports server-side
  3. Smart Matching — A weighted algorithm automatically compares LOST and FOUND reports
  4. Claim & Verify — Claimant answers a verification question; verified server-side
  5. Approve & Resolve — Finder approves or rejects; approved claims mark item as recovered

3. Core Workflow

Student A loses a laptop
        ↓
Reports it on LostLink (title, category, location, description, date)
        ↓
Student B finds a laptop
        ↓
Reports it with a verification question:
"What brand is the laptop and what color sticker is on it?"
        ↓
Matching Engine compares the two reports → Score: 94% (Very Strong Match)
        ↓
Student A sees the match, claims the item
        ↓
Answers: "HP, blue sticker"
        ↓
Backend verifies answer (never exposed to frontend)
        ↓
Correct → Claim PENDING
        ↓
Student B approves
        ↓
Item RESOLVED — Item Recovered

4. Key Features

4.1 User Authentication

  • Register and login with email/password
  • JWT-based session management (7-day token expiry)
  • Passwords hashed with bcryptjs (never stored plaintext)
  • Rate limiting: 20 requests per 15 minutes on auth endpoints

4.2 Lost & Found Reporting

  • 10-step multi-step form for detailed reporting
  • Basic info: title, category, description
  • Item details: brand, model, color, size, distinctive features
  • Location with type (bus, train, school, office, etc.)
  • Identification: serial number, IMEI, engravings, unique markings
  • Photo upload with previews
  • For FOUND items: verification question and answer
  • Ownership proof and security information
  • Contact preferences and privacy settings

4.3 Search & Filtering

  • Server-side search by title, description, category, location, brand
  • Filter by type (LOST/FOUND), category, status, date
  • Pagination support (12 items per page)
  • All filtering happens in MongoDB — no client-side overhead

4.4 Smart Matching Engine

A weighted scoring algorithm compares every LOST item against every FOUND item (and vice versa):

FactorWeightScoring Logic
Category30%Same category = 30, different = 0
Location25%Jaccard similarity on normalized tokens; exact = 25, similar = partial
Description25%Jaccard keyword similarity (stop words filtered)
Date20%Same day = 20, 1 day = 15, 2 days = 10, 3 days = 5

Match Strength Labels:

  • 90–100% Very Strong Match
  • 75–89% Strong Match
  • 60–74% Possible Match
  • Below 60%: Not displayed

Only opposite types are compared (LOST ↔ FOUND). Resolved items are excluded. Top 5 matches returned.

4.5 Claim & Verification

  • User claims a FOUND item by answering the verification question
  • Answer verified server-side (case-insensitive, trimmed)
  • Verification answer is never exposed to the frontend
  • Correct answer → Claim PENDING, item → CLAIM_PENDING
  • Finder approves → Claim APPROVED, item → RESOLVED
  • Finder rejects → Claim REJECTED, item → ACTIVE
  • All other pending claims on same item auto-rejected on approval

4.6 Dashboard

  • Total lost items, found items, matches, recovered items
  • Recent activity feed
  • Quick actions to report or browse

7. Matching Algorithm

Located in server/services/matchingService.js.

Processing Flow

  1. Fetch the source item
  2. Determine opposite type (LOST → search FOUND, FOUND → search LOST)
  3. Fetch all active opposite-type items (exclude resolved, exclude self)
  4. For each candidate, calculate four sub-scores
  5. Sum scores, filter below 60%, sort descending, return top 5

Scoring Details

FactorWeightLogic
Category30Exact string match (case-insensitive) = 30, else 0
Location25Normalize → tokenize → Jaccard similarity. ≥0.7 = 23, ≥0.4 = 18, >0 = 10, partial token match = 8
Description25Normalize → remove stop words → tokenize → Jaccard similarity × 25
Date20Same day = 20, 1 day diff = 15, 2 days = 10, 3 days = 5, >3 = 0

Text Processing

  • Lowercase
  • Remove punctuation
  • Trim whitespace
  • Remove stop words: the, a, an, with, and, is, was, near, at, in, on, of, to, for, it, this, that, or, but, not, be, are, from
  • Tokenize by space
  • Remove tokens with length ≤ 1

Match Output

{
  item: { id, title, type },
  matches: [
    {
      item: { id, title, description, category, type, location, date, image },
      score: 94,
      strength: "VERY_STRONG",
      reasons: ["Same category", "Same location", "Similar description", "Same date"]
    }
  ]
}

8. Claim & Verification Flow

User claims FOUND item
        ↓
Enters verification answer
        ↓
Backend verifies answer (never exposed to frontend)
        ↓
    Correct? —— YES → Claim PENDING
              —— NO  → 400 "Incorrect verification answer"
        ↓
Finder reviews claim
        ↓
    Approve? → Claim APPROVED → Item RESOLVED
              All other pending claims → REJECTED
    Reject?  → Claim REJECTED → Item ACTIVE
